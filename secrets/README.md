# secrets/

The machine-secret store: API keys, bot tokens, R2 credentials, the crypt password, Google's OAuth client — everything a `bin/` script reads. Human logins and passkeys are not here; they belong in your password manager.

| File                   | What                                                                                                   | In the template | In your instance |
| ---------------------- | ------------------------------------------------------------------------------------------------------ | --------------- | ---------------- |
| `README.md`            | this file                                                                                              | yes             | yes              |
| `secrets.example.yaml` | the shape of the store: every `<name>.<field>` the wrappers read, values empty                         | yes             | yes              |
| `secrets.yaml`         | the store, [sops](https://github.com/getsops/sops)-encrypted to [age](https://age-encryption.org) keys | **never**       | committed        |
| `backup.pub`           | public half of the paper backup key                                                                    | **never**       | committed        |
| `hosts/<box>.yaml`     | a headless box's own values (designed, not built — below)                                              | **never**       | when built       |
| `../.sops.yaml`        | generated by `secrets recipients`: who the store is encrypted to                                       | **never**       | committed        |

Key names in `secrets.yaml` are plaintext; only the values are encrypted. That is what lets `secrets status`, `secrets check`, `security-check` and the pre-commit hook reason about the file without decrypting it — and it is why your instance repo must stay private: the names say which services you use.

## Keys

- **One age key per manager machine**, at `~/.config/sops/age/keys.txt` (directory 700, file 600), made by `secrets init`. It never leaves the machine and is never in a repo. Its public half is the `age_recipient:` line in that machine's `docs/machines/<host>.md`.
- **One paper backup key**, made by `secrets backup-key` in a terminal: the private half is printed once for you to write down twice, on two sheets kept in two places; the public half goes to `backup.pub`. `secrets backup-verify` has you type it back and proves it opens the store. Losing every machine key and both sheets loses every secret, including the password that encrypts `~/resources` in R2.
- There is no unlock step. The key file is the credential; at rest it relies on FileVault (Linux: LUKS) and mode 600, so launchd jobs and hooks keep working unattended.

## Rules

- Write only through `secrets set`, `secrets import-env` or the wrappers. Never open the file in an editor, never `sops edit` — `secrets` keeps values off the command line and out of logs.
- Every non-empty value must be `ENC[…]`. `security-check`, the pre-commit hook and the stop hook all refuse anything else.
- Claude never decrypts. It may run `secrets status` and `secrets check`; it is asked before `init`, `set --from-file`, `import-env`, `recipients`, `admit`, `revoke`, `push` and `exec` (a command run with secrets in its environment can send them anywhere, so `exec` is never allowed outright); it is denied `env`, `backup-key`, `backup-verify`, and every `sops` command that prints or edits values.

## Adding and removing a machine

1. On the new machine, after `/setup` maps it: `secrets init` (makes its key, records `age_recipient`, commits).
2. On a manager that can already read the store: `git pull && secrets admit <new-host>` (re-encrypts the data key to include it, commits).
3. On the new machine: `git pull`, then `secrets status` says `recipient: yes`.

Removing one: `secrets revoke <host>` on a manager that stays. It drops the host's recipient, re-encrypts, and rotates the data key — then prints every secret that host could read. Git history still holds the old ciphertext, which the old key opens, so **rotate each of those values at its provider** (`/rotate <name>`). Revocation is only as good as that step.

## Client secrets

A credential a client shares with you lives in that client's repo, not in this store: `~/clients/<name>/secrets/secrets.yaml`, a sops file encrypted to the same recipients. Its repo is private (`new-client` makes it so, `security-check` fails it otherwise), and the pre-commit hook it was given refuses plaintext there too. Once, in the client folder:

```bash
cp ~/claude-computer/.sops.yaml . && mkdir -p secrets && echo '{}' > secrets/secrets.yaml
sops --config .sops.yaml encrypt -i secrets/secrets.yaml
```

Then a human sets values with `CC_ROOT="$PWD" CC_SECRETS_FILE="$PWD/secrets/secrets.yaml" secrets set <name>.<field>`, and after the fleet admits or revokes a machine, copies `.sops.yaml` again and runs `sops --config .sops.yaml updatekeys -y secrets/secrets.yaml` there.

## Headless boxes (designed, not built)

Headless boxes hold no secrets today and have no clone. When the first one needs one:

- `secrets/hosts/<box>.yaml` holds only that box's values, encrypted to the box's own age key, every manager and the backup key — a second `creation_rules` entry in `.sops.yaml`.
- The box's `age_recipient:` goes in its machine file like any other; its key is made on the box.
- `secrets push <box>` copies the ciphertext (never plaintext) to `/etc/claude-computer/secrets.yaml` on the box, where a pinned sops release binary reads it.

Until then, `secrets push` says so and exits 5.
