# Why the template is built this way

The reasoning behind the defaults in this repo. Your instance's own log is `docs/DECISIONS.md`, which starts empty; supersede any of these there when you change it.

- Link the contents of `claude-global/` into `~/.claude` (CLAUDE.md, settings.json, commands/, hooks/), not the directory — `~/.claude` also holds session transcripts and state that must never enter a repo.
- rclone remotes defined from the secrets store through environment variables per run; no `rclone.conf` with keys on disk — a plaintext copy of a key anywhere else would break the no-plaintext-secrets rule.
- Secrets never on a command line: curl reads auth headers and tokenised URLs from stdin config — argv is visible to every process via `ps`.
- Scripts target bash 3.2 (macOS system bash) or Python via `uv run --script` — a new machine has neither a newer bash nor a managed Python when setup starts.
- Stop hook commits and pushes `docs/` at the end of every turn, not only at session end — sessions are often killed rather than exited.
- Template marked by a `.template` file; the pre-commit hook refuses machine files while it exists and `/setup` deletes it in an instance — a remote-URL check would break for forks and renames.
- Biome (not ESLint + Prettier) in the VS Code list and scaffolds, matching DEV-GUIDELINES — one tool, one config.
- Scheduled jobs are defined in `bin/schedule` and installed as launchd user agents with a `local.claude-computer.` prefix — one place to read the schedule; `map-check` sees them as launchd drift until recorded.
- Headless browsing is Playwright with its bundled Chromium, wrapped as `bin/browse` (markdown by default, screenshot, PDF, persistent profiles); never `chrome --headless` — the Chrome cask stays for the human and for Claude in Chrome, and a pinned Playwright Chromium is reproducible and scriptable.
- Playwright and Chromium are installed by `setup-tools.sh` (the step for things Homebrew can't install), pinned to the version in `bin/browse`'s script header — browser builds must match the library version.
- `feeds-sync` falls back to `browse --md` when Firecrawl returns a teaser or fails; the web scaffold uses Playwright for end-to-end tests — one browser engine for scraping and testing.
- `browse` profiles (`~/.config/browse/profiles/<name>`) hold logged-in sessions: mode 700, never in a repo, listed under Sensitive locations in each machine file, checked by `security-check`, unreadable by Claude in settings — they are credentials in all but name.
- `rg` is the one search tool, configured once for every agent. Agents do not share a search implementation: Claude Code's native build runs `rg` from the shell and wraps `grep`/`find` in embedded `ugrep`/`bfs`; Codex is told to prefer `rg`; Gemini CLI and Qwen Code spawn `rg --json`. The wrapped `grep` searches hidden files and ignores `.ignore`, so it returns different files from `rg` for the same pattern — the global `CLAUDE.md` names `rg` so results don't depend on which tool a model reached for.
- `dotfiles/ripgreprc` caps printed lines at 200 bytes and does nothing else. One match in a minified file measured 40 KB of output without it and under 300 bytes with it. It never changes what matches — no globs, no `--smart-case` — because a config that silently alters results is its own drift; `--json` output is unaffected, so tools that parse it are too. `RIPGREP_CONFIG_PATH` is exported from `dotfiles/zshenv`, not `zshrc`: agents' shells are non-interactive and never read `zshrc`. `map-check` verifies both.
- `ast-grep` is in the base Brewfile for structural search in Python and TypeScript: on a four-line test, `rg` returned a call, a comment and a string literal alike, and `ast-grep` returned only the two real calls. It is the one tool added on its own documentation rather than an agent vendor's recommendation, and it skips files without an extension, so `rg` stays the default.
- Scaffolds ship a `.ignore` listing lockfiles, minified files and source maps — committed files `.gitignore` can't hide. Only `rg` and `fd` read it, which is one more reason for the `rg` rule.
- `rg --pre` and `--hostname-bin` run a program of the caller's choosing, so they are ask rules even though plain `rg` is allowed (Codex shipped a CVE, 2025-54558, for auto-approving them).
- The terminal is Ghostty running **herdr** in every window: one persistent session whose sidebar shows each coding agent as working, blocked, done or idle (read from each pane's screen, so no hook is needed), with macOS notifications when an agent finishes or needs you. Running several Claude sessions at once is the normal case here, and herdr is the piece that says which one is waiting. Ghostty's ⌘ shortcuts are remapped to herdr's `ctrl+b` sequences (`keybind = cmd+t=text:\x02c` …), written by hand rather than with the native-shortcuts-herd installer, so the whole mapping is visible in one file. `window-save-state = never`: herdr keeps the session, and Ghostty restoring old windows opened a duplicate workspace per window. herdr's own version check is off; Homebrew updates it.
- The prompt is a powerlevel10k-"rainbow" look-alike in Starship (frame, rounded segments, status / duration / versions / clock on the right) sized for a herdr pane: about 74 columns normally and 88 at worst against a measured 92-column pane beside the sidebar. The path is at most two folders, from the repo root inside a repo; the host shows only over SSH. Icons are Nerd Font glyphs, so the font is MesloLGS Nerd Font **Mono**, whose icons are one cell wide — what keeps those widths true. The colours are Solarized Dark (Ghostty's `iTerm2 Solarized Dark`; the `Builtin Solarized …` names the old config used don't exist in Ghostty 1.3), with herdr's sidebar one shade lighter.
- `dotfiles/zshrc` aliases no standard command name. Claude Code snapshots the user's aliases into its Bash tool, so `ls` → `eza` and `cat` → `bat` changed what a model's `ls -lt` or `cat -A` did (eza and bat parse those flags differently or reject them). `eza` and `bat` stay installed under their own names and `ll`.
- `claude-global/settings.json` sets `PAGER=cat`, `GIT_PAGER=cat`, `GH_PAGER=cat` and `NO_COLOR=1` for every command Claude runs — the same environment Codex gives its shell — so a pager can never block a command and colour codes never reach the context. It applies to Claude's subprocesses only, not to the user's terminal.
- The global `CLAUDE.md` asks for summary-first commands (`git status -sb`, `git diff --stat`, `jq -c`, `gh --json … --jq`): measured on a small repo, 327 → 59 bytes for status and 630 → 116 for a diff. Habits, not a filtering proxy — output-compressing wrappers were considered and declined because a wrapper that can swallow an exit code or misreport a failed test run costs more than it saves.
- `~/clients` holds one private repo per client (`new-client`), with `brief/` tracked: the client's documents are the most important thing in it, and without a repo they exist on one machine only. Code for a client is a separate repo inside the folder, which the client repo ignores (`new-client` and `new-app` both add it). `security-check` fails if a client repo is public. An earlier draft moved all work into `~/ai`, grouped by who it is for; it was dropped before release — the home folder's top level already does that grouping, and a second level only adds typing.
- Inside `clients/`, `projects/`, `products/` and `personal/`, a folder without a `CLAUDE.md` may group the repos of one thing (a site and an API); `tasks-sync` looks one level into it. Anything deeper is not discovered — one level of grouping is enough.
- No Syncthing, superseding "a working folder between my own machines". Two machines writing the same `.git` through a two-way sync can corrupt it, a deletion on one machine deletes everywhere, and git (code, notes, client documents) and R2 (archive, media) already give every folder one way off the machine.
- Agent Reach gives Claude the platforms the `bin/` wrappers don't cover (YouTube, GitHub, RSS, and social channels the user opts into). It is a router and health check, not a wrapper: its skill points Claude at upstream CLIs (`yt-dlp`, `gh`, `mcporter`), so it costs one skill description of standing context — the same reason the wrappers exist. `mcporter` calls an MCP server from the command line, per call, so Exa's server is never loaded into a session.
- `setup-tools.sh` installs Agent Reach from a pinned commit, never `main` — the package installs a skill Claude follows, so an upgrade is a deliberate, reviewed change. A commit rather than the latest tag because v1.5.0 predates the consent-gated `install --system` and the hidden-input `configure`, while `main` still reports 1.5.0. Since the version string can't tell builds apart, `map-check` compares the URL in uv's install receipt with the pin.
- Only Agent Reach's zero-config channels are installed. Every optional channel keeps a cookie or key in `~/.agent-reach/config.yaml` or drives a logged-in Chrome — a stated exception to "secrets live only in the sops store", so it is the user's opt-in per channel, entered by them through `agent-reach configure <key>` with no value on the command line (hidden prompt), recorded in `DECISIONS.md`. The file is a sensitive location, unreadable by Claude in settings, and `security-check` fails if it is not mode 600.
- Voice capture is MacParakeet (on-device Parakeet, Homebrew cask). Completed transcriptions reach the vault through `bin/transcripts-sync`, which reads its SQLite database read-only — a launchd WatchPaths agent plus the SessionStart hook, so meetings arrive without asking.
- `transcripts-sync` is idempotent twice over: a per-machine cursor on (updatedAt, id), because each machine has its own database; and a `macparakeet_id` in every note, checked across `inbox/transcripts` and `sources/transcripts`, so a lost cursor never duplicates. Notes still unprocessed are refreshed when edited in the app; processed ones are never overwritten.
- Files, URLs and podcasts are transcribed straight into `vault/inbox/transcripts` with `macparakeet-cli transcribe … --no-history`, keeping them out of the database the sync reads. Short dictation goes into `vault/inbox/quick.md` with no script — the cheapest capture wins.
- Transcript processing produces a five-line summary note, links people, routes action items to the owning brain's `## Next` with a backlink, and files the raw transcript in `sources/transcripts` as processed. Action items with no owner go to `vault/TASKS.md` `## Unassigned` rather than being guessed into a brain.
- `## Unassigned` is an overflow with a hard exit: rendered first in `maps/tasks.md`, emptied by every `/review` (owner or Later), and `tasks-sync` alerts once a day when it passes 10 — an unowned list otherwise grows forever.
- MacParakeet's two macOS permissions (Microphone; Screen Recording for system audio) and its Parakeet v3 model download are human steps; `map-check` verifies `macparakeet-cli health --json` afterwards.
- README diagrams are hand-laid SVG generated by `docs/diagrams/render.py` (light and dark variants, served through `<picture>`), replacing Mermaid — Mermaid's auto-layout couldn't produce swimlanes or a readable map; the generator keeps the source in text and reviewable.
- Permission mode is **auto** (`defaultMode: auto` in `claude-global/settings.json`, linked as user settings), superseding auto-accept edits — a classifier reviewing each action fits all-day operator sessions better than a static allow-list, and explicit ask rules (push, rm, rclone, sudo, storage scripts) and deny rules still hold in auto mode. Never bypassPermissions. Scheduled `claude -p` jobs pass `--permission-mode auto`, since `-p` otherwise starts in manual mode.
- `daily-note` is the only job that runs Claude unattended, and it is constrained rather than trusted: `~/vault` is its working directory, so that is the tree it may edit, and `--allowedTools` narrows it to `Read,Edit,Write,Glob,Grep` plus `git status`/`add`/`commit` — a list derived from what drafting and committing a note actually needs. Auto mode alone is not enough here, because the fallback when the classifier is unsure is to ask, and at 06:30 there is nobody to ask. Any scheduled job that runs Claude gets the same treatment.
- Secrets never on a command line, including on the way into the store: `secrets set` and `import-env` hand each value to `sops set --value-stdin` through a pipe, and `lib/cc.py` passes the Google token to `secrets set --stdin` the same way — the Bitwarden-era `set_note()` put it in `bw`'s argv, where every process could see it in `ps`.
- `--delete-local` in `archive-push` asks before each `rm -rf`, through `cc_confirm`, which answers no without a terminal — the upload is verified by then, but "verified" and "you meant to destroy the only other copy" are different claims. `--yes` carries an answer the user has already given; `/archive` passes it only after they have.
- Scaffold placeholders are `__NAME__`, not `{{name}}` — `{{…}}` is just's interpolation syntax, so a `{{name}}` in a justfile is a just variable that does not exist.
- `jq` is installed in `/setup` phase 4, before the hooks are linked, not left to `brew bundle` in phase 6 — every hook parses its stdin with `jq`, and hooks linked without it run degraded rather than failing visibly.
- The vault and its plugins are installed by `bin/vault-setup`, not assumed — the `obsidian` cask alone left a fresh Mac with the app, no vault, and a brain naming three plugins (Obsidian Git, Dataview, Templater) that nothing installed, while `_templates/` was already Templater syntax and the README claimed the vault synced through git. Each plugin's repo is looked up by id in Obsidian's `community-plugins.json` registry rather than hard-coded (there are fallbacks for the day the registry cannot be read, checked against the manifest id like anything else), and `main.js`/`manifest.json`/`styles.css` come from that repo's latest GitHub release, verified and moved into place whole.
- Plugin binaries are **not** committed to the vault repo: `.obsidian/plugins/*/main.js` and `styles.css` are gitignored, while `manifest.json`, `data.json` and the generated `.source.json` are committed. Settings must travel between machines; downloaded code is not the notes repo's business, and `vault-setup` restores it from the version recorded in `.obsidian/plugins/VERSIONS.md`.
- Obsidian's own settings are never clobbered: `community-plugins.json` is merged (the three ids added to whatever is there), and every other file — `app.json`, `daily-notes.json`, Templater's and Obsidian Git's `data.json` — is written only when it does not exist. A setting changed in the app outlives every re-run.
- Obsidian Git is configured for manual commits and a pull when the vault opens (all intervals 0, `autoPullOnBoot`) — the vault brain has Claude committing after each job, and a plugin committing on a timer underneath that produces two writers and merge conflicts in a notes repo. `map-check`/`security-check` check that the vault's origin is not public instead of trusting that nobody added a remote by hand.
- `vault-setup`'s work directory is inside the vault, so the move into `.obsidian/plugins/` is a rename on one filesystem — and it is removed before anything is staged. A `git add -A` with it still there committed a 2.3 MB copy of the plugin registry and then deleted it: junk in the history, a dirty tree, and a 27-second gitleaks scan on a brand-new vault. The shared pre-commit hook was already staged-only and needed no change.
- Permission rules for it are exact allows plus ask patterns that name `--create-remote`, because Claude Code evaluates deny, then ask, then allow, and specificity does not change that: one broad `Bash(vault-setup:*)` ask would have made every allow entry beneath it dead weight and prompted for `--dry-run` too.
- `--create-remote` is a separate flag, never implicit, and `/setup` must ask before passing it: `gh repo create` publishes the second brain, and a repo of that name that is already public is refused outright.
- Turning off Obsidian's restricted mode stays a human step. Obsidian decides it per vault and keeps the answer outside the config files this script writes, so `vault-setup` presets what it can (the plugin list) and prints the one click precisely. The Web Clipper is a browser extension and is printed the same way.
- Machine secrets live in `secrets/secrets.yaml`, a [sops](https://github.com/getsops/sops) file encrypted to [age](https://age-encryption.org) keys, committed to the private instance — one age key per manager at `~/.config/sops/age/keys.txt` (dedicated, not the SSH key) plus one paper backup key whose public half is `secrets/backup.pub`. Open source end to end, no account or server, the same on Linux boxes, and nothing to unlock: the key file is the credential, protected at rest by FileVault/LUKS and mode 600, so launchd jobs and hooks work unattended. A passphrase on the key or a Secure Enclave key (`age-plugin-se`) was declined because either breaks unattended jobs.
- `.sops.yaml` is generated by `secrets recipients` from each machine file's `age_recipient:` frontmatter plus `secrets/backup.pub`, never edited by hand — the machine files are already the fleet's list of machines, and a second hand-kept list would drift. Scripts run sops from `CC_ROOT` with `--config`, and export `SOPS_AGE_KEY_FILE`, because sops's macOS default is `~/Library/Application Support/sops/age/keys.txt` and launchd and hooks never read `~/.zshenv`.
- Verified on sops 3.13.3 and age 1.3.2 (2026-10-04) before building on them: `sops set --value-stdin` first shipped in **sops 3.11.0**, which `lib/common.sh` (`CC_SOPS_MIN`) requires for writes and CI pins, so CI proves the floor. `sops decrypt --extract` prints the value with **no trailing newline**. Exit codes: **1** for a path not in the file, **100** for a missing file, **128** when no key can open the data key, **7** for a non-JSON `--value-stdin` value. sops leaves **empty strings unencrypted** (`token: ""` stays as is), so "every value is `ENC[`" means every non-empty value. `sops updatekeys` keeps the data key and `sops rotate -i` replaces it; both worked with `--config` and an absolute path from another directory. `sops exec-env` refuses a nested file ("cannot use complex value in environment") and runs its command through a shell string, so `secrets exec` decrypts once to JSON and exports the chosen values itself.
- No `.gitleaks.toml`: the plan expected gitleaks to flag `ENC[AES256_GCM,…]` lines, but gitleaks 8.30.1 found nothing in a store of 100+ encrypted values under names like `api_key`, `password`, `secret_access_key` and `token`, while it caught an age private key twice (`age-secret-key` and `generic-api-key`). An allowlist that isn't needed would only be a place for a real leak to hide; `tests/secrets.sh` asserts both behaviours in CI instead, so a gitleaks change that starts flagging ciphertext fails there first.
- Key names in the store are plaintext; values are not. That is what lets `secrets status`/`check`, `security-check`, the pre-commit hook and the stop hook reason about the file without decrypting it, and it is why the instance repo must stay private. Values never become an argument: reads come back on stdout into a variable, writes go `printf` → `jq -Rs` → `sops set --value-stdin` through pipes, and `tests/secrets.sh` logs every sops and jq argv to prove it.
- `secrets import-env` moves a plaintext dotenv file into the store in one pass: well-known variable names map to the paths the wrappers read (`TAVILY_API_KEY` → `tavily.api_key`, `R2_ACCESS_KEY_ID` → `r2.access_key_id` …) and anything else goes to `env.<name lowercased>`; it prints names and counts, never a value, and skips values already set unless `--overwrite`. `secrets exec --only NAME,… -- <cmd>` replaces "source the dotenv in a subshell": it gives one command exactly the secrets it names. `exec` is an ask rule for Claude and never allowed — a command run with secrets in its environment can send them anywhere — and `secrets env`, which prints them, is denied.
- Per-host secret files for headless boxes (`secrets/hosts/<box>.yaml`, pushed as ciphertext to `/etc/claude-computer/secrets.yaml`) are designed in `secrets/README.md` and not built: no box needs a secret yet, and `secrets push` says so.
- Claude never decrypts, and the rules are built for that rather than for exceptions: deny is evaluated before ask before allow, so no "allow `sops decrypt` of this one path" is possible, and anything `--extract` printed would land in Claude's context anyway. Only the wrappers decrypt. `secrets set` takes a typed value only at a terminal prompt, so typing stays human; a program pipes a value with `--stdin`, which Claude is denied, and Claude may run `set --from-file` behind an ask, which keeps the value out of its context. `secrets exec` is ask, never allow — the command it runs can send the secrets anywhere. These are still pattern matches, not a sandbox.
- Bitwarden was removed in 0.5.0, superseding "Bitwarden session token kept in the macOS login Keychain". It needed an account, a server and an unlock per login that unattended jobs couldn't do, it does not run on a headless Linux box without a session, and one lost master password locked every script out. sops + age needs none of those. Human logins were never the scripts' business and stay in whichever password manager the user prefers.
- Client secrets live in a sops file in each client's own repo (`secrets/secrets.yaml` there, encrypted to the same recipients), not as `clients.<name>` in the fleet store: the client's credentials travel and are deleted with the client's repo, and the fleet store's key names don't list clients.
- Every manager gets every secret, rather than per-machine subsets: there are a handful of managers, all the user's own, and subsets would turn every new machine into a decision about which secrets it may hold.
- `rm` is guarded by a hook, not an ask rule. Claude Code checks ask rules before allow rules and before a hook's decision, so with `Bash(rm:*)` on the ask list nothing could let `rm` run in a temporary folder unprompted. An allow rule like `Bash(rm -rf /tmp/*)` is no substitute: `*` matches any text, spaces included, so it would also match `rm -rf /tmp/x ~/work`, and rules match command text without resolving `..`. The hook parses the command and resolves every path, allows only the narrow safe case, asks for every other `rm`, and asks if anything goes wrong.
- The Python and TypeScript LSP plugins are enabled in the shared settings and their servers live in `Brewfile.dev`, so every dev machine gets symbol navigation and post-edit diagnostics the same way. The servers are Homebrew formulas rather than `npm -g` installs, so `brew bundle` and `map-check` see them; cloud sessions don't run language servers, and grep stays the fallback there.
- Long tasks get a live progress page, `.dashboard/index.html` in the project, made by `bin/dashboard`. It is a file, not a server: it opens with a double-click, works offline, reloads itself every 10 seconds, and needs no port, process or cleanup. `.dashboard/` is in `dotfiles/gitignore_global`, so it is never committed by accident.
- The layout is designed by a model once per task, and every later update is a script changing facts. Routine updates then cost nothing and can't drift in style, and a model never writes data: every timestamp comes from the computer's clock, and a row keeps its time when its contents don't change, so "last update" means a fact changed, not that someone ran a command.
- The designer (`claude-global/agents/dashboard-designer.md`) runs as `claude -p` with `--tools ""`, `--strict-mcp-config`, `--setting-sources ""`, `--disable-slash-commands` and `--system-prompt-file`, from an empty temporary folder. Checked on Claude Code 2.1.289 (2026-10-04): in that mode it reports no tools, no CLAUDE.md, no memory and no skills, and `--setting-sources ""` also keeps the user's hooks from firing on it. It is not linked into `~/.claude/agents`, because a subagent started through the Agent tool would inherit context it must not have. `--bare` would isolate it further but reads only `ANTHROPIC_API_KEY`, which a subscription login doesn't have. Model and effort (Sonnet, medium) come from the agent file's frontmatter.
- The designer's output is treated as untrusted. Its HTML may use only a list of layout elements and attributes — no scripts, links, images, forms or `style` attributes — and must place every data slot exactly once, empty; its CSS may not contain `url(`, `@import`, `@font-face`, backslashes or `<`. A rejected answer gets one retry with the reasons; a second rejection fails with them, and the last good page stays. No fallback layout and no other model: a page that looks right but wasn't designed or validated is worse than a clear failure. The page's Content-Security-Policy allows exactly one script, the clock, by its hash, as a second line of defence.
- The style is asked once and saved in `~/.config/claude-dashboard/style.json` (light or dark, dense or airy, one accent colour, or a brand file read at design time). It is per user, not per project, so every dashboard looks familiar. `dashboard init` refuses without one and says what to ask, because a script can't ask the user and Claude can.
- Documentation is Markdown with front matter, plus generated files for each kind of reader: `llms.txt` and JSON for agents, one static `index.html` for people. One source means nothing drifts; the front matter's `summary`, `depends_on` and `answers` let an agent pick the one file it needs instead of reading everything; and the build checks every link and anchor, so docs fail like code does. The standard comes from a real project's design docs, whose generated files the shared build reproduces byte for byte (apart from the "generated by" comment).
- The build is one shared script, `bin/docs-build`, rather than a copy in every repo, so a fix reaches every project at once; generated files are committed, so nobody needs the script to read the docs. Client repos are the exception: `--vendor` gives them a self-contained `build.py`, because the people who build them don't have this repo. Project-specific checks live in the project's `docs_ext.py`, not in the shared script.
- The fleet brain's own `docs/` keeps its operational formats (machine files, `FLEET.md`, `DECISIONS.md`): they are records with their own contracts (`map-check` reads the machine files), not documentation about a design. `docs-build --view` gives them the same reading page without asking them to change.
- GA4 and PostHog split by question, not by tool quality. PostHog answers what people do inside the product (features, retention, sessions, flags); GA4 through Google Tag Manager answers where visitors come from and which of them convert, in the terms ad platforms and marketing reports use. An event goes to one of them, not both, so numbers never need reconciling.
- `analytics.yaml` is the source of truth for a site's GA4 and Tag Manager setup, and funnels and reports live in that file too. GA's API cannot save an Explore exploration, so a funnel built in the UI could not be created, reviewed or reproduced by a script; named in the file, it is versioned and diffed like code and `analytics funnel` / `analytics report` run it on demand. Created IDs are written back to the file so the project carries its own state.
- `analytics sync` saves a container version but never publishes; `analytics publish` is a separate command and Claude asks before every run. Publishing changes what a live site sends to Google and cannot be taken back quietly, so it stays a deliberate step after Preview mode, and the scope that allows it is the one thing the wrappers are told never to use unprompted.
- The rm-guard hook ships but is not wired into `claude-global/settings.json` by default: some owners would rather be asked about every `rm`, and a hook that decides on its own is a policy to opt into. So `Bash(rm:*)` is on the ask list by default, and every `rm` prompts. To use the hook instead, remove `Bash(rm:*)` from the ask list (an ask rule wins over a hook's decision) and add a `PreToolUse` entry with matcher `Bash` and a command hook running `~/.claude/hooks/rm-guard.py` (timeout 10). `CC_RM_GUARD=off` in a machine's environment (for example `env` in `~/.claude/settings.local.json`) turns it off there. This narrows the earlier entry that `rm` is guarded by a hook: the hook is still the right mechanism, only no longer the default.
