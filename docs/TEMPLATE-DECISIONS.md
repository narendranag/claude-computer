# Why the template is built this way

The reasoning behind the defaults in this repo. Your instance's own log is `docs/DECISIONS.md`, which starts empty; supersede any of these there when you change it.

- Link the contents of `claude-global/` into `~/.claude` (CLAUDE.md, settings.json, commands/, hooks/), not the directory — `~/.claude` also holds session transcripts and state that must never enter a repo.
- Bitwarden session token kept in the macOS login Keychain (Linux: `$XDG_RUNTIME_DIR`) so every wrapper and hook shares one unlock — hooks and Claude's shell don't share environment, and a plaintext session file would break the no-plaintext-secrets rule.
- rclone remotes defined from Bitwarden through environment variables per run; no `rclone.conf` with keys on disk — same rule.
- Secrets never on a command line: curl reads auth headers and tokenised URLs from stdin config — argv is visible to every process via `ps`.
- Scripts target bash 3.2 (macOS system bash) or Python via `uv run --script` — a new machine has neither a newer bash nor a managed Python when setup starts.
- Stop hook commits and pushes `docs/` at the end of every turn, not only at session end — sessions are often killed rather than exited.
- Template marked by a `.template` file; the pre-commit hook refuses machine files while it exists and `/setup` deletes it in an instance — a remote-URL check would break for forks and renames.
- Biome (not ESLint + Prettier) in the VS Code list and scaffolds, matching DEV-GUIDELINES — one tool, one config.
- Scheduled jobs are defined in `bin/schedule` and installed as launchd user agents with a `local.claude-computer.` prefix — one place to read the schedule; `map-check` sees them as launchd drift until recorded.
- Headless browsing is Playwright with its bundled Chromium, wrapped as `bin/browse` (markdown by default, screenshot, PDF, persistent profiles); never `chrome --headless` — the Chrome cask stays for the human and for Claude in Chrome, and a pinned Playwright Chromium is reproducible and scriptable.
- Playwright and Chromium are installed by `setup-tools.sh` (the step for things Homebrew can't install), pinned to the version in `bin/browse`'s script header — browser builds must match the library version.
- `feeds-sync` falls back to `browse --md` when Firecrawl returns a teaser or fails; the web scaffold uses Playwright for end-to-end tests — one browser engine for scraping and testing.
- `browse` profiles (`~/.config/browse/profiles/<name>`) hold logged-in sessions: mode 700, never in a repo, listed under Sensitive locations in each machine file, checked by `security-check`, unreadable by Claude in settings — they are credentials in all but name.
- Voice capture is MacParakeet (on-device Parakeet, Homebrew cask). Completed transcriptions reach the vault through `bin/transcripts-sync`, which reads its SQLite database read-only — a launchd WatchPaths agent plus the SessionStart hook, so meetings arrive without asking.
- `transcripts-sync` is idempotent twice over: a per-machine cursor on (updatedAt, id), because each machine has its own database; and a `macparakeet_id` in every note, checked across `inbox/transcripts` and `sources/transcripts`, so a lost cursor never duplicates. Notes still unprocessed are refreshed when edited in the app; processed ones are never overwritten.
- Files, URLs and podcasts are transcribed straight into `vault/inbox/transcripts` with `macparakeet-cli transcribe … --no-history`, keeping them out of the database the sync reads. Short dictation goes into `vault/inbox/quick.md` with no script — the cheapest capture wins.
- Transcript processing produces a five-line summary note, links people, routes action items to the owning brain's `## Next` with a backlink, and files the raw transcript in `sources/transcripts` as processed. Action items with no owner go to `vault/TASKS.md` `## Unassigned` rather than being guessed into a brain.
- `## Unassigned` is an overflow with a hard exit: rendered first in `maps/tasks.md`, emptied by every `/review` (owner or Later), and `tasks-sync` alerts once a day when it passes 10 — an unowned list otherwise grows forever.
- MacParakeet's two macOS permissions (Microphone; Screen Recording for system audio) and its Parakeet v3 model download are human steps; `map-check` verifies `macparakeet-cli health --json` afterwards.
- README diagrams are hand-laid SVG generated by `docs/diagrams/render.py` (light and dark variants, served through `<picture>`), replacing Mermaid — Mermaid's auto-layout couldn't produce swimlanes or a readable map; the generator keeps the source in text and reviewable.
- Permission mode is **auto** (`defaultMode: auto` in `claude-global/settings.json`, linked as user settings), superseding auto-accept edits — a classifier reviewing each action fits all-day operator sessions better than a static allow-list, and explicit ask rules (push, rm, rclone, sudo, storage scripts) and deny rules still hold in auto mode. Never bypassPermissions. Scheduled `claude -p` jobs pass `--permission-mode auto`, since `-p` otherwise starts in manual mode.
- `daily-note` is the only job that runs Claude unattended, and it is constrained rather than trusted: `~/vault` is its working directory, so that is the tree it may edit, and `--allowedTools` narrows it to `Read,Edit,Write,Glob,Grep` plus `git status`/`add`/`commit` — a list derived from what drafting and committing a note actually needs. Auto mode alone is not enough here, because the fallback when the classifier is unsure is to ask, and at 06:30 there is nobody to ask. Any scheduled job that runs Claude gets the same treatment.
- Secrets never on a command line, including the Bitwarden session token itself: the macOS Keychain write goes through `security -i`, which reads its commands from stdin, rather than `security add-generic-password -w "$token"`, whose argument every process can see in `ps`. The read path returns the token on stdout, so only the item's service name is ever an argument.
- `--delete-local` in `archive-push` asks before each `rm -rf`, through `cc_confirm`, which answers no without a terminal — the upload is verified by then, but "verified" and "you meant to destroy the only other copy" are different claims. `--yes` carries an answer the user has already given; `/archive` passes it only after they have.
- Scaffold placeholders are `__NAME__`, not `{{name}}` — `{{…}}` is just's interpolation syntax, so a `{{name}}` in a justfile is a just variable that does not exist.
- `jq` is installed in `/setup` phase 4, before the hooks are linked, not left to `brew bundle` in phase 6 — every hook parses its stdin with `jq`, and hooks linked without it run degraded rather than failing visibly.
- The vault and its plugins are installed by `bin/vault-setup`, not assumed — the `obsidian` cask alone left a fresh Mac with the app, no vault, and a brain naming three plugins (Obsidian Git, Dataview, Templater) that nothing installed, while `_templates/` was already Templater syntax and the README claimed the vault synced through git. Each plugin's repo is looked up by id in Obsidian's `community-plugins.json` registry rather than hard-coded (there are fallbacks for the day the registry cannot be read, checked against the manifest id like anything else), and `main.js`/`manifest.json`/`styles.css` come from that repo's latest GitHub release, verified and moved into place whole.
- Plugin binaries are **not** committed to the vault repo: `.obsidian/plugins/*/main.js` and `styles.css` are gitignored, while `manifest.json`, `data.json` and the generated `.source.json` are committed. Settings must travel between machines; downloaded code is not the notes repo's business, and `vault-setup` restores it from the version recorded in `.obsidian/plugins/VERSIONS.md`.
- Obsidian's own settings are never clobbered: `community-plugins.json` is merged (the three ids added to whatever is there), and every other file — `app.json`, `daily-notes.json`, Templater's and Obsidian Git's `data.json` — is written only when it does not exist. A setting changed in the app outlives every re-run.
- Obsidian Git is configured for manual commits and a pull when the vault opens (all intervals 0, `autoPullOnBoot`) — the vault brain has Claude committing after each job, and a plugin committing on a timer underneath that produces two writers and merge conflicts in a notes repo. `map-check`/`security-check` check that the vault's origin is not public instead of trusting that nobody added a remote by hand.
- `vault-setup`'s work directory is inside the vault, so the move into `.obsidian/plugins/` is a rename on one filesystem — and it is removed before anything is staged. A `git add -A` with it still there committed a 2.3 MB copy of the plugin registry and then deleted it: junk in the history, a dirty tree, and a 27-second gitleaks scan on a brand-new vault. The shared pre-commit hook was already staged-only and needed no change.
- Permission rules for it are exact allows plus ask patterns that name `--create-remote`, because Claude Code evaluates deny, then ask, then allow, and specificity does not change that: one broad `Bash(vault-setup:*)` ask would have made every allow entry beneath it dead weight and prompted for `--dry-run` too.
- `--create-remote` is a separate flag, never implicit, and `/setup` must ask before passing it: `gh repo create` publishes the second brain, and a repo of that name that is already public is refused outright.
- Turning off Obsidian's restricted mode stays a human step. Obsidian decides it per vault and keeps the answer outside the config files this script writes, so `vault-setup` presets what it can (the plugin list) and prints the one click precisely. The Web Clipper is a browser extension and is printed the same way.
